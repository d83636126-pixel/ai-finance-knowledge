# 产品发展执行计划 V3.2：真实事件摄入与日常推进

## 0. 定稿结论

V3.2 不重建事件系统。它只把现有日历、Inbox、突发事件入口和 V3.1 台账接成一条真实日常循环。

> 用户在台账中发现候选事件，确认后立即进入现有 registry，并按照时间形态进入事前跟踪、持续跟踪、待复盘或待核验。

## 1. 当前真实缺口

V3.1 台账目前：

- 能读取 registry；
- 能读取未来 30 天日历候选；
- 候选事件的“纳入研究”仍跳回传播图；
- 台账不直接读取 Inbox 候选；
- 确认纳入后没有原地状态反馈；
- 时间未定和突发/持续事件仍依赖分散入口。

因此 V3.1 回答了“已纳入事件先做什么”，但没有回答“新事件如何持续进入”。

## 2. 用户主路径

```text
打开事件台账
→ 查看统一候选区
→ 核对来源与时间状态
→ 确认纳入
→ 卡片原地变成正式事件
→ 打开研究记录
→ 补事前准备或事实节点
→ 返回台账继续下一条
```

## 3. 产品范围

### 3.1 统一候选区

候选区合并展示：

- 尚未纳入的日历事件；
- Inbox/新闻候选；
- 已明确将发生但准确时间未知的事件；
- 已经发生的突发事件；
- 需要持续更新的政策、监管或地缘事件。

每条候选必须显示：

- 标题和来源；
- 已知时间、时间窗口或“时间待核验”；
- 候选类型；
- 为什么进入候选区；
- 一个主动作：`确认纳入`。

### 3.2 台账内确认纳入

- 日历与 Inbox 复用既有服务端纳入能力；
- 客户端只提交权威候选 ID，不手工拼正式记录；
- 纳入成功后卡片原地更新；
- 同一候选重复确认必须幂等；
- 成功后可以一次点击打开对应研究记录；
- 失败必须显示原因，不允许假装成功。

### 3.3 四种时间形态

| 时间形态 | 用户显示 | 纳入后状态 |
|---|---|---|
| 准确时间 | 明确日期与时区 | `TRACKING_PRE` 或待复盘 |
| 时间窗口 | 显示起止窗口 | `TRACKING_PRE` / `ONGOING` |
| 明确将发生但时间未知 | 时间待核验 | `NEEDS_REVIEW`，仍可建立记录 |
| 突发或持续事件 | 已发生/持续中 | 待复盘或 `ONGOING` |

不得为时间未知事件伪造一个准确日期。

### 3.4 日常任务摘要

台账顶部显示：

- 新候选；
- 未来 7 天；
- 缺少事前准备；
- 持续事件待补事实；
- 已发生待复盘；
- 信息待核验。

这里只做确定性计数和跳转，不做 AI 评分。

## 4. 执行批次

### Batch A：候选合流

- 台账读取日历与 Inbox 候选；
- 建立统一候选展示模型；
- 明确来源、时间状态和候选类型；
- 测试/验证候选默认隔离。

### Batch B：台账内确认与原地反馈

- 接通日历和 Inbox 权威纳入入口；
- 幂等和失败可见；
- 成功后原地切换生命周期；
- 进入正确研究记录。

### Batch C：真实事件日常走查

- 使用真实事件覆盖五类样本；
- 完成“候选—纳入—记录—返回台账”；
- 验证事件到达前后状态；
- 形成最终产品验收材料。

Batch A–C 内部连续执行，不分别开启审核。

## 5. 真实验收样本

至少覆盖：

1. 一个已在日历中的未来事件；
2. 一个 Inbox 新闻候选；
3. 一个明确将发生但时间未定的事件；
4. 一个已经发生的财报、政策或突发事件；
5. 一个持续发展的政策或地缘事件；
6. 一个需要时间/身份/数据核验的事件。

样本可以使用当前或已经发生的真实事件，不等待未来发布日期。

## 6. 验收场景

### 场景 A：日历候选

在台账确认纳入，卡片原地变成事前跟踪，并打开正确研究记录。

### 场景 B：Inbox 候选

确认权威 Inbox 项目，创建稳定 `event_id`；再次确认不重复创建。

### 场景 C：时间未知事件

允许纳入并保存研究记录，但显示待核验，不出现虚构时间。

### 场景 D：突发/持续事件

纳入后可以记录事实节点，并在台账显示持续跟踪或待复盘。

### 场景 E：状态推进

使用显式 `evaluated_at` 验证未来、进行中和已发生状态，不等待真实日期。

## 7. PASS 标准

全部满足才可写入 `EVENT_DAILY_LOOP_V1_PASS`：

- 台账同时展示日历和 Inbox 候选；
- 用户两次点击以内完成“候选 → 纳入 → 打开研究记录”；
- 纳入成功后无需跳转传播图或手动刷新；
- 重复确认不产生第二条 registry 记录；
- 时间未知事件可保存且不会伪造时间；
- 突发/持续事件可以进入正确生命周期；
- 测试记录不进入真实候选和优先队列；
- 真实五类样本集中走查通过；
- 创建、保存、打开、返回台账路径完整。

## 8. 明确不做

- 不重写 registry；
- 不新增数据库；
- 不做复杂抓取平台；
- 不自动纳入未确认新闻；
- 不做 AI 事件评分；
- 不做跨事件比较；
- 不做日报推送；
- 不做研究有效性验证；
- 不因普通 UI 微调增加审核轮次。

## 9. 回滚与停止条件

- 新候选区可通过单一开关隐藏，V3.1 台账仍可使用；
- 新纳入动作失败时不得修改原候选状态；
- 若发现正式 registry 被测试数据污染，立即停止写入并恢复只读候选；
- 若两次集中修正后主路径仍无法完成，停止 V3.2，交 Human 重新裁剪范围。

## 10. 开环条件

只有以下条件满足后才开 `PRD-EVENT-DAILY-10`：

1. Human 批准本计划；
2. 当前交接板仍为 V3.1 `done/human`；
3. 产品基线锁定为 `8b4f576`；
4. 本环单独提交，不纳入既有无关脏文件；
5. 不并行 V3.3。

本文落盘不等于 V3.2 已开环。

- Human 已在 `http://127.0.0.1:8013/event_research_registry.html` 完成集中产品走查；
