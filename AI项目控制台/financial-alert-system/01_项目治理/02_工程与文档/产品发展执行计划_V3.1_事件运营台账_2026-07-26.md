# 产品发展执行计划 V3.1：事件运营台账

## 0. 定稿结论

V3.1 不重建 registry，也不重新开发日历、Inbox、研究记录或事件收尾卡。

本阶段只解决一个产品问题：

> 用户打开系统后，能否在一分钟内知道现在最该处理哪条事件，并通过一个明确动作进入正确的研究步骤？

V3.1 将已有事件来源、research registry、统一研究记录和事件收尾卡组织成一个“事件运营台账”。

```text
分散的事件能力
→ 一个统一台账
→ 明确生命周期
→ 明确优先原因
→ 一个主动作
```

本计划完成后才可开启 `PRD-EVENT-REGISTRY-09`。本文落盘不等于代码环已经开始。

---

## 1. 产品目标与用户价值

### 1.1 一句话目标

> 用户进入事件运营台账，在 60 秒内找到当前最该处理的事件，并一次点击进入纳入、事前准备、持续跟踪或事件收尾卡。

### 1.2 用户为什么打开台账

用户不是为了浏览所有字段，而是为了回答：

1. 今天有哪些事件需要处理？
2. 哪些即将发生但事前准备不足？
3. 哪些已经发生但尚未复盘？
4. 哪些持续事件出现了新节点？
5. 哪些事件已经完成，可以重新打开结果？
6. 哪些记录存在时间、来源或身份问题，需要先核验？

### 1.3 产品成功后的变化

当前：

```text
打开日历
→ 打开工作台
→ 查看研究记录
→ 猜测事件状态
→ 再寻找结果页
```

V3.1 后：

```text
打开事件运营台账
→ 看到“现在最该处理”
→ 点击唯一主动作
→ 完成任务
→ 返回台账查看下一条
```

## 3. 当前数据现实与可见性规则

### 3.1 当前快照

计划编写时，本地 registry 包含 23 条记录，混合了：

- 真实日历事件；
- 历史 retrospective 验证样本；
- smoke/时间门禁测试记录；
- Inbox 集成测试残留；
- 可能代表同一真实事件的多个身份。

该现象不要求进行数据库重构，但若直接全部展示，会让用户把测试记录或重复身份误认为真实待办，因此属于 V3.1 的产品正确性边界。

### 3.2 默认视图分类

台账读取现有数据后，只做非破坏性的展示分类：

| 分类 | 默认展示 | 处理方式 |
|---|---|---|
| `PRODUCT` | 是 | 进入活跃台账和优先级排序 |
| `VALIDATION` | 否 | 可在“验证样本”筛选中查看，不进入今日优先级 |
| `TEST` | 否 | 默认完全隐藏，只在开发诊断模式显示 |
| `IDENTITY_REVIEW` | 是，但不参与正常优先级 | 显示“身份待核验”，禁止静默合并 |
| `TIME_REVIEW` | 是 | 显示“时间待核验”，禁止进入事后动作 |

### 3.3 最小分类依据

- `source=test`、`adopted_from=test` 或 `event_id` 以 `test_` 开头 → `TEST`；
- `smoke_fixture=true` 且不是显式测试记录 → `VALIDATION`；
- 无法解析时间或应有时间却为空 → `TIME_REVIEW`；
- 只有存在明确身份冲突证据时才标记 `IDENTITY_REVIEW`，不得仅凭标题相似自动合并；
- 其余记录作为 `PRODUCT` 候选。

### 3.4 数据处理边界

- V3.1 不删除任何现有 registry 记录；
- 不根据标题自动合并事件；
- 不修改 historical/legacy 标签；
- 不把 validation 样本升级成真实产品事件；
- 发现重复身份时只显示核验入口，后续由明确规则处理；
- 默认视图不得把测试记录列入“现在最该处理”。

## 4. 生命周期与状态语言

### 4.1 主生命周期

每条事件只能显示一个主生命周期：

| 生命周期 | 人话名称 | 判定含义 | 主动作 |
|---|---|---|---|
| `CANDIDATE` | 待纳入 | 来自日历/Inbox，但尚未进入 registry | 纳入研究 |
| `TRACKING_PRE` | 事前跟踪 | 未来事件，时间可核验 | 打开研究记录 |
| `ONGOING` | 持续跟踪 | 事件正在发展或窗口尚未结束 | 记录新节点 |
| `OCCURRED_PENDING_RESULT` | 已发生待复盘 | 时间已过，尚无完整收尾卡 | 完成事件收尾卡 |
| `REVIEWED` | 已复盘 | 已有可重开的事件收尾卡 | 打开收尾卡 |
| `NEEDS_REVIEW` | 信息待核验 | 时间、身份或关键来源不可靠 | 核验信息 |

### 4.2 本阶段暂不增加 ARCHIVED 写操作

当前 registry 没有稳定的显式归档字段。V3.1 不为了补齐一个状态而扩展存储和恢复流程。

- 已复盘事件统一进入“已完成”；
- 归档写操作延后，除非实现过程中发现已有可靠字段可直接复用；
- 不允许页面自行猜测“已归档”。

### 4.3 辅助提示

每条事件最多两个辅助提示：

- 缺事前快照；
- 时间待核验；
- 身份待核验；
- 来源不足；
- 已知历史复盘；
- 证据过期；
- 结果有修订。

辅助提示只描述风险或行动，不表示研究结论正确。

## 5. 优先级排序

### 5.1 原则

排序必须确定、可解释，不使用 AI 评分。

每条进入“现在最该处理”的事件必须显示排序原因，例如：

- “已发生 3 天，尚未复盘”；
- “48 小时内发生，缺少事前记录”；
- “持续事件有新事实节点”；
- “发布时间未知，需要先核验”。

### 5.2 默认优先级

从高到低：

1. 已发生但尚未完成收尾卡；
2. 持续事件出现新节点；
3. 7 天内即将发生且缺事前准备；
4. 时间或身份待核验；
5. 7 天内即将发生且已有事前准备；
6. 7 天外的未来事件；
7. 已复盘事件。

### 5.3 “现在最该处理”区域

- 最多展示 3 条；
- 不展示 `TEST` 或 `VALIDATION`；
- 每条只给一个主动作；
- 分数或内部字段不直接展示；
- 同优先级时按事件时间升序，再按 `event_id` 稳定排序；
- 页面显示本次排序的 `evaluated_at`。

## 6. 页面结构

拟新增入口：

`event_research_registry.html` — 页面标题“事件运营台账”

### 6.1 顶部：现在最该处理

最多三张行动卡：

- 事件名称；
- 距离发生/已发生时间；
- 主生命周期；
- 排序原因；
- 一个主按钮。

### 6.2 第二层：生命周期分组

- 待纳入；
- 即将发生；
- 持续跟踪；
- 已发生待复盘；
- 已完成；
- 信息待核验。

### 6.3 最小筛选

- 生命周期；
- 事件类型；
- 时间范围；
- 来源；
- 是否有事前记录；
- 是否有事件收尾卡。

不做无限自定义筛选器。

### 6.4 记录卡片

每张记录卡只显示：

- 名称和 `event_id`；
- 时间或时间待核验；
- 一个主状态；
- 最多两个辅助提示；
- 一个主动作；
- 一个“查看详情”次动作。

技术标签和完整 refs 默认折叠。

### 6.5 错误与空态

- registry API 不可用 → 明确显示加载失败，不展示假数据；
- 没有活跃事件 → 显示如何从日历/Inbox 纳入；
- 候选源不可用 → 已纳入事件仍可显示；
- 状态无法判定 → 进入“信息待核验”，不得默认为正常；
- 事件动作打开错误 `event_id` → 产品阻断。

## 7. 真实样本计划

### 7.1 当前可直接使用的产品样本

| 用途 | 事件 | 计划角色 |
|---|---|---|
| 即将发生 | `earnings_nvda_2026_q2` | 未来事件、打开研究记录 |
| 即将发生 | `earnings_aapl_2026_q2` | 未来事件、排序与筛选 |
| 已发生待复盘 | `earnings_googl_2026_q2` | 时间已过、进入事件收尾卡 |
| 已发生待复盘 | `earnings_msft_2026_q2` | 同类记录稳定排序 |
| 时间待核验 | `cpi_2026_06` | `scheduled_at` 缺失，进入核验区 |

具体时间必须在执行时重新核验，不以本计划快照作为事实真相源。

### 7.2 必须通过正常入口补入的样本

V3.1 执行时需选择一条当前真实持续事件，通过现有日历或 Inbox 纳入路径进入 registry，用于验证 `ONGOING`。

要求：

- 不手工伪造 registry 文件；
- 保留来源和采集时间；
- 若事件时间不确定，明确使用窗口或“时间待核验”；
- 不把历史验证样本冒充当前持续事件。

### 7.3 验证样本

`earnings_googl_2025_q2` 等 V3.0 historical/validation 记录只用于验证“已完成事件可重开”，必须显示历史/验证边界，不进入当前优先队列。

## 8. 内部执行批次

A–C 是同一产品环内部批次，不分别开审核。

### Batch A：台账视图契约

- 建立非破坏性的可见性分类；
- 建立唯一生命周期派生逻辑；
- 建立确定性优先级和原因说明；
- 接入现有 registry、结果存在性和候选来源；
- 默认排除 TEST/VALIDATION 优先级污染。

### Batch B：事件运营台账页面

- 新增台账页面；
- 加入统一工作台主入口；
- 实现顶部 3 条优先行动；
- 实现生命周期分组和最小筛选；
- 每条事件连接到正确研究记录或收尾卡；
- 错误、空态和核验状态 fail-loud。

### Batch C：真实事件集中走查

- 未来事件；
- 持续事件；
- 已发生待复盘；
- 已复盘验证样本；
- 时间待核验；
- 测试记录默认不可见；
- 身份冲突不静默合并。

Batch C 完成后才进入一次集中产品验收。

## 9. 产品验收

### 9.1 验收名

`EVENT_RESEARCH_REGISTRY_V1_PASS`

该 PASS 只表示事件运营台账产品路径可用，不表示研究结论、数据质量或预测能力通过。

### 9.2 Human 集中走查

一次完成以下任务：

1. 打开台账；
2. 在 60 秒内指出当前最该处理的事件；
3. 说明该事件为什么排在第一；
4. 一次点击进入正确研究记录；
5. 从已发生待复盘事件进入正确收尾卡；
6. 找到一条即将发生事件；
7. 找到一条持续事件；
8. 找到一条时间待核验事件；
9. 找到一条已完成历史复盘；
10. 确认测试门禁记录不出现在默认视图。

### 9.3 PASS 条件

全部满足：

- 60 秒内找到当前首要事件；
- 排序原因清楚且可复现；
- 主生命周期与事件事实一致；
- 每条记录只有一个主动作；
- 目标页面和 `event_id` 正确；
- 时间未知、来源不足和身份问题不会被伪装成正常；
- 测试/验证记录不污染活跃优先级；
- 已有 registry 保持唯一真相源；
- 不绕过 RESULT 时间门禁；
- 页面错误时不显示静默 mock；
- 三种以上生命周期完成真实走查。

### 9.4 CHANGES_REQUIRED 边界

仅以下问题阻断：

- 错误事件或错误 `event_id` 被打开；
- 测试记录进入真实优先队列；
- 未来事件能够绕过时间门禁生成事后结果；
- 数据被覆盖、删除或错误合并；
- 生命周期造成事实错误；
- 主路径无法加载、筛选或打开；
- 历史验证样本被包装为当前前瞻事件。

普通文案、颜色微调、更多负向测试、性能优化和非关键筛选登记为后续优化，不开启新一轮技术验收。

## 10. 明确不做

- 不做独立 BADGE 环；
- 不做新数据库或 registry 迁移；
- 不做自动事件合并；
- 不做复杂相关性和跨事件统计；
- 不做投资组合管理；
- 不做多人协作、权限或云同步；
- 不做 AI 自动排序；
- 不做研究评分和排行榜；
- 不跑 held-out/forward 研究验收；
- 不宣称 `RESEARCH_PASS`、`DATA_QUALITY_PASS` 或 `RELEASE_PASS`；
- 不重开 V3.0 技术整改。
