# 项目产品现状与下一阶段发展路线图 V1

## 0. 结论先行

项目不需要再次进行整体架构重构，也不需要重新审核已经完成的 V1–V3.0。

当前需要的是一次产品层面的重新排序。结论如下：

1. V3.0“真实事件结果与复盘”已经完成并归档；
2. 项目已经具备事件发现、纳入、研究记录、待办执行、结果记录和事件收尾卡等能力；
3. 当前最大产品缺口，是这些事件仍分散在日历、Inbox、研究记录和结果页中，用户没有一个地方集中判断“现在最该处理什么”；
4. 下一唯一产品环确定为 V3.1“事件运营台账”；
5. BADGE 只作为台账中的最小状态表达，不单独研发；
6. V3.1 完成前不并行跨事件比较、研究评分、上云或新的技术加固。

```text
下一步不是重做系统
而是把已有能力组织成可持续使用的产品
```

## 1. 产品定位

### 1.1 系统现在是什么

financial-alert-system 目前应被定义为：

> 面向单个研究者的本地事件研究运营系统：从真实事件发现与纳入开始，保留事前信息，跟踪事件进展，在事件发生后完成结果复盘，并把结论沉淀为以后可以重新使用的事件资产。

它不是单纯的行情看板，也不是只为 NFP 服务的回测工具，更不是已经证明预测有效的自动研究模型。

### 1.2 核心用户任务

用户真正需要完成的是：

```text
今天有哪些事件值得处理？
→ 我应该纳入哪一条？
→ 这条事件现在处于什么阶段？
→ 当前应该补事实、补事前判断、继续跟踪，还是做结果复盘？
→ 以前相似事件留下了什么可复用结论？
```

### 1.3 产品承诺

- 少手工造事件；
- 不在多个页面寻找同一条事件；
- 每条事件始终有明确下一步；
- 已发生事件能够形成可重开的收尾卡；
- 历史复盘不会被包装成提前判断；
- 产品可用性与研究有效性严格分开。

### 2.1 已经形成的闭环

```text
真实事件来源
→ 纳入 research registry
→ 打开统一研究记录
→ 执行研究待办并回写 refs
→ 事件发生
→ 打开事件收尾卡
→ 保存、重开和复制摘要
```

这条单事件路径已经完成，不应再次作为下一阶段的技术整改对象。

### 2.2 尚未形成的闭环

```text
多个真实事件同时存在
→ 用户打开系统
→ 快速判断优先级
→ 找到当前最该处理的事件
→ 执行与生命周期一致的下一步
→ 完成后自动回到新的优先队列
```

这正是 V3.1 需要解决的产品问题。

## 3. 当前主要产品问题

### P1：事件存在，但用户缺少总览

registry 已经能够保存和列出事件，但用户需要分别打开日历、工作台、研究记录和结果页才能判断状态。

影响：

- 不知道当前最该处理哪条事件；
- 已发生待复盘事件容易被遗漏；
- 已完成复盘难以重新找到；
- 即将发生和持续事件无法在一个视图比较优先级。

### P2：生命周期存在于字段和页面中，没有形成统一用户语言

当前事件可能具有发布时间、事前快照、结果文件、证据状态和来源标签，但没有统一地转换为用户可理解的阶段与动作。

影响：

- 不同页面可能使用不同说法；
- 用户看到状态后仍不知道下一步；
- 技术标签容易挤占产品主视图。

### P3：真实当前事件尚未成为稳定的日常使用循环

项目已经处理历史事件和特定 NFP 案例，但对即将发生、明确将发生但尚未进入日历、突发及持续事件，还缺少统一的每日操作入口。

影响：

- 产品仍容易被理解为验收样机；
- 无法持续积累新的事前记录；
- 复盘能力有了，但事件资产增长速度不足。

### P4：已完成事件还没有转化为可复用资产

事件收尾卡已经包含“下次关注什么”，但用户不能按事件类型查找这些结论，也无法方便地用于下一条同类事件。

该问题重要，但必须在 V3.1 台账完成并积累更多真实事件后处理。

---

## 4. 优先级原则

下一阶段排序不以“哪个技术包还没做”为依据，而按以下顺序：

1. **使用频率**：是否影响每次打开产品；
2. **主路径摩擦**：是否让用户在多个页面反复寻找；
3. **积累价值**：是否让每完成一条事件都增加未来价值；
4. **已有基础**：是否可复用现有 registry、记录页和结果页；
5. **可独立验收**：是否不依赖未来日期或研究有效性；
6. **边界清晰**：是否能在一个集中产品验收中结束。

据此，事件运营台账优先于 BADGE、复杂比较、模型评分和更多数据源扩展。

## 5. 下一阶段路线图

## 5.1 V3.1：事件运营台账（下一唯一执行环）

### 产品目标

> 用户打开一个页面，在一分钟内找到现在最该处理的事件，并通过一个主动作进入正确的研究步骤。

### 拟定执行环

- loop：`PRD-EVENT-REGISTRY-09`
- 验收：`EVENT_RESEARCH_REGISTRY_V1_PASS`
- 轨道：`PROD`
- 审核：整环一次集中产品验收
- 状态：本路线图只确定方向，尚未开环

### 核心页面结构

事件运营台账只需要五个区域：

1. **现在最该处理**：最多 3 条，按明确规则排序；
2. **即将发生**：已有日期或明确窗口的事件；
3. **持续跟踪**：战争、关税实施、监管进程等持续事件；
4. **已发生待复盘**：事件已经发生但收尾卡未完成；
5. **已复盘/已归档**：可以重新打开和复制摘要的事件资产。

### 每条事件必须回答

- 这是什么事件；
- 何时发生或当前时间是否待核验；
- 当前生命周期；
- 为什么排在这里；
- 下一步唯一主动作；
- 是否已有事前记录；
- 是否已有事件收尾卡。

### 最小用户动作

| 生命周期 | 唯一主动作 |
|---|---|
| 候选事件 | 纳入研究 |
| 即将发生 | 打开研究记录 / 补事前信息 |
| 持续事件 | 记录新事实节点 |
| 已发生待结果 | 完成事件收尾卡 |
| 已复盘 | 打开收尾卡 / 复制摘要 |
| 已归档 | 查看或恢复 |

### BADGE 的位置

BADGE 不作为独立产品环，只是上述生命周期和风险的紧凑显示：

- 一个主生命周期标识；
- 最多两个辅助提示；
- 不用绿色暗示研究结论正确；
- 不展示内部六子机制名称；
- 不在不同页面重新发明状态。

### 真实事件验收集

必须使用至少五类真实记录：

- 一个已进入日历、尚未发生的事件；
- 一个明确将发生但时间仍待核验的事件；
- 一个持续事件；
- 一个已发生待复盘事件；
- 一个已完成事件收尾卡的事件。

### 产品验收

全部满足才可 PASS：

- 用户在 60 秒内找到“现在最该处理”的事件；
- 每条事件只有一个清晰主动作；
- 一次点击进入正确研究记录或事件收尾卡；
- 即将发生、持续、待复盘、已复盘四类记录均真实可见；
- 筛选后 `event_id` 不错配；
- 时间未知、证据缺失和历史复盘边界可见；
- 不创建第二套 registry；
- 不需要用户理解工程门禁或六子机制；
- 三条不同生命周期主路径完成集中走查。

### 明确不做

- 不重写 registry 存储；
- 不做复杂自定义查询；
- 不做多人权限、云同步或公开分享；
- 不做独立 BADGE 工程；
- 不做跨事件统计；
- 不新增研究评分；
- 不因普通视觉微调追加复审。

## 5.2 V3.2：当前与未来事件日常循环

V3.1 完成后，再让台账持续吸收和推动真实当前事件。

### 目标

> 日历事件、已明确将发生的事件和突发/持续事件，可以进入同一个日常处理队列，并在时间到达后自然转入结果复盘。

### 最小范围

- 日历候选一键纳入；
- Inbox/新闻候选经用户确认纳入；
- 时间未确定事件显示“时间待核验”；
- 突发/持续事件允许追加事实节点；
- 事件到达后进入“待复盘”；
- 使用真实事前记录，不等待特定 NFP 日期才能验收产品流程。

### 验收边界

本阶段验证真实日常使用循环，不验证预测准确率，也不能单独触发 `RESEARCH_PASS`。

---

## 5.3 V3.3：跨事件复用与同类比较

只有在台账中积累了足够真实事件后才开启。

### 目标

> 用户准备下一条同类事件时，能够快速找到过去事件的实际结果、关键偏差和“下次关注什么”。

### 最小范围

- 按事件类型查找已复盘事件；
- 并排查看 2–3 条事件收尾卡摘要；
- 提取过去记录中的“下次关注”；
- 将选中的观察点复制到新事件待办；
- 明确显示历史/retrospective 边界。

### 不做

- 不做预测胜率排行榜；
- 不从少量历史事件推导统计规律；
- 不自动生成“方法论已验证”结论；
- 不在样本不足时输出可靠性 PASS。

## 6. 暂缓能力

以下能力没有被取消，但当前不应占用产品主线：

| 能力 | 处理方式 |
|---|---|
| 独立 BADGE 环 | 取消；并入 V3.1 最小状态语言 |
| 研究评分/排行榜 | 延后到真实 forward 证据充分后再评估 |
| held-out/forward 研究验收 | 与产品开发解耦，被动积累，不阻塞 V3.1–V3.3 |
| 更多技术负向测试 | 仅在数据损坏、安全或事实错误风险出现时增加 |
| 新数据库/上云 | 当前本地单用户产品不需要 |
| 多人权限/协作 | 当前不做 |
| 大规模前端重写 | 当前不做；复用已有页面和视觉语言 |
| 自动 AI 长研报 | 当前不做 |

## 7. 审核与治理方式

### 7.1 产品优先

每个阶段先证明用户路径，再做必要技术验证。普通命名、更多反例、性能优化和测试数量不作为继续拖延产品主线的理由。

### 7.2 审核节点

每个完整产品环只设：

1. 开始前一次范围确认；
2. 完成后一次集中产品验收。

内部页面、接口和测试步骤不分别开审核环。

### 7.3 可阻断问题

只有以下问题可以阻断产品 PASS：

- 数据被错误覆盖或错配；
- 时间或事实判断明显错误；
- 用户无法创建、保存、打开或复盘事件；
- 下一步动作进入错误事件或绕过时间门禁；
- 历史复盘被包装成前瞻判断；
- 安全或不可恢复的数据风险。

其他问题登记为技术债或产品优化项。
