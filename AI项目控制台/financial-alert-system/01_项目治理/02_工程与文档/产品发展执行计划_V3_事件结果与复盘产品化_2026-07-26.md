# 产品发展执行计划 V3：事件结果与复盘产品化

> [!important] 2026-07-26 状态更新
>
> V3.0 RESULT 已完成并归档。原本文档中的 V3.1 REGISTRY/BADGE 方向已由《项目产品现状与下一阶段发展路线图 V1》重新排序：下一阶段只开产品型事件运营台账，BADGE 并入最小状态语言，不单独开环。本文保留为 V3 原始规划依据，不再作为当前执行入口。

## 0. 计划结论

V2.2–V2.7 已经完成事件的纳入、统一记录、增量提示、待办、单条/批量就地执行以及 refs 回写稳定性。

V3 不再继续围绕旧链路补测试或修边角，而是解决尚未完成的产品问题：

> 事件发生以后，系统怎样把事前判断、实际结果、市场反应和传播路径验证，沉淀成以后可以检索、比较和复用的研究成果？

V3 只开两个产品能力批次：

1. **V3.0 RESULT：真实事件结果与复盘闭环**
2. **V3.1 REGISTRY：事件研究台账 + BADGE 状态标识**

BADGE 不单独开环；它是 RESULT 与 REGISTRY 状态的视觉表达。

V3 整体成功标准：

`EVENT_RESEARCH_PRODUCT_V3_PASS`

该结论只表示事件研究产品 V3 的用户流程成立，不表示：

- `RESEARCH_PASS`
- `DATA_QUALITY_PASS`
- `RUNTIME_ACCEPTANCE_PASS`
- `RELEASE_PASS`
- 模型预测有效
- held-out / forward 研究验收完成

## 1. 为什么进入 V3

### 1.1 V2 已经解决的问题

| 能力 | 已有结果 |
|---|---|
| 事件入口 | 已有日历事件可纳入研究，不必重新手造 |
| 统一身份 | 复用稳定 `event_id`，重复纳入幂等 |
| 研究记录 | 服务端 registry 为真相源，可保存、重开 |
| 事前/事后 | 已有生成入口和未来事件门禁 |
| 路径与证据 | 可编排已有 Graph、传播路径和证据刷新 |
| 待办 | 能看到缺事前、缺证据、待事后的记录 |
| 执行 | 支持单条与批量就地执行 |
| 状态同步 | refs / `evidence.refreshed_at` 回写已稳定 |

### 1.2 V2 尚未解决的问题

当前系统更接近“事件准备与跟踪工具”，还不是完整的“研究结果沉淀工具”：

- 事件发生后，实际结果没有形成统一、可复用的结果页。
- 事前判断与事后事实之间缺少稳定对照。
- 市场反应、传播路径是否成立、判断偏差没有形成结构化复盘。
- 多条事件缺少按生命周期组织的研究台账。
- 页面状态提示存在，但没有形成统一、可信的产品状态语言。

如果继续只修旧链路，用户仍会问：

> 这条事件最后发生了什么？原判断哪里对、哪里错？下次同类事件该看什么？

V3 必须直接回答这个问题。

## 2. 用户与核心任务

### 2.1 主要用户

项目所有者本人，用于宏观、政策、财报、地缘冲突及突发事件的持续跟踪与复盘。

本阶段不以外部客户、多租户或公开服务为目标。

### 2.2 核心任务

当一条事件已经发生或进入可复盘状态时，用户能够：

1. 打开既有研究记录；
2. 看见事件发生前留下的判断、路径和证据；
3. 确认实际发生的事实及来源；
4. 记录事件后的市场反应；
5. 判断事前预期与传播路径是否成立；
6. 留下下次可复用的观察结论；
7. 保存、重开、检索并复制一页复盘。

### 2.3 核心价值

V3 必须同时提供两类增量：

- **少干活**：复用现有事件、事前记录、路径和证据，不重新填写一套事件。
- **有积累**：每完成一条事件，系统多一份以后能找到、能比较、能复用的结果。

## 3. V3 支持的事件范围

V3 不能只围绕尚未发生的 NFP，也不能因未来日期未到而停滞。

### 3.1 已发生事件

可立即进入 RESULT：

- 已公布的宏观数据；
- 已发布的大型机构财报；
- 已实施或已公布结果的关税、制裁、政策事件；
- 已发生的战争、冲突、谈判或地缘节点；
- 已完成窗口的行业、公司或市场事件。

若事件及结果在纳入系统前已经为用户所知，必须标记：

`RETROSPECTIVE / 已知历史复盘`

它可以验证产品流程和帮助总结经验，但不能充当前瞻证据。

### 3.2 已进入日历、尚未发生的事件

进入事前跟踪：

- 保留预计时间或时间窗口；
- 形成事前快照；
- 事件发生前不得生成事后结果；
- 到时后自动或人工转为“待确认结果”。

V3 产品验收不等待某一条未来事件真的发生。

### 3.3 未进入日历、但已明确将发生的事件

允许以“明确预告事件”纳入：

- 必须保留公告或可靠来源；
- 时间不精确时使用时间窗口，不伪造精确时刻；
- 标记 `ANNOUNCED_WINDOW`；
- 在正式日历信息出现后，可补齐时间，但保持同一 `event_id` 或明确合并关系。

### 3.4 突发或持续事件

战争、制裁、政策突变等可能没有单一结束时间：

- 允许状态为 `ONGOING`；
- 以关键节点形成多次事实更新；
- 每个阶段可形成阶段性结果；
- 不强迫一次性标记“完成”。

## 4. 单一事件生命周期

V3 使用一套产品生命周期，避免 RESULT、REGISTRY、BADGE 各自定义状态。

```text
CANDIDATE
  ↓ 纳入
TRACKING_PRE
  ↓ 已发生或发布时间已到
OCCURRED_PENDING_RESULT
  ↓ 确认实际事实并完成复盘
REVIEWED
  ↓ 不再持续跟踪
ARCHIVED
```

持续事件允许：

```text
TRACKING_PRE / OCCURRED_PENDING_RESULT
  ↔ ONGOING
  → REVIEWED（阶段性或最终）
```

### 4.1 状态定义

| 状态 | 含义 | 用户下一步 |
|---|---|---|
| `CANDIDATE` | 已发现但尚未纳入 | 纳入研究或忽略 |
| `TRACKING_PRE` | 已纳入，事件尚未发生 | 补事前、刷新证据、等待事件 |
| `OCCURRED_PENDING_RESULT` | 已发生或时间窗已过，尚未确认结果 | 确认实际结果并复盘 |
| `ONGOING` | 事件持续发展，暂无单一终点 | 记录关键节点和阶段性结果 |
| `REVIEWED` | 已形成可复用复盘 | 重开、复制、比较 |
| `ARCHIVED` | 结束活跃跟踪但保留记录 | 检索或恢复 |

状态必须由统一规则派生，不允许页面各自猜测。

## 5. V3.0：RESULT 真实事件结果与复盘闭环

### 5.1 一句话目标

> 不重新创建事件，十分钟内完成一条真实事件的“事前—实际—反应—路径—结论”复盘，并能保存、重开和复制。

### 5.2 验收名

`EVENT_RESEARCH_RESULT_V1_PASS`

### 5.3 用户主路径

1. 在日历、研究待办或研究记录中打开一条已发生事件。
2. 系统展示冻结的事前信息：
   - 当时的事前判断；
   - 当时的影响路径；
   - 当时已有证据及时间；
   - 事前快照时间。
3. 用户确认实际结果：
   - 实际发生了什么；
   - 发生或公布时间；
   - 来源；
   - 是否存在修订或不确定性。
4. 用户记录市场反应：
   - 观察对象；
   - 观察窗口；
   - 方向和幅度（有可靠数据时）；
   - 暂无数据时明确标记缺失，不静默补值。
5. 用户完成研究复盘：
   - 事前预期：命中 / 部分命中 / 未命中 / 无法判断；
   - 传播路径：成立 / 部分成立 / 未成立 / 证据不足；
   - 最大偏差；
   - 下次同类事件应重点观察什么。
6. 保存为一页复盘摘要。
7. 关闭后重开，结果保持一致；支持复制摘要。

### 5.4 RESULT 最小产品结构

| 区域 | 必须内容 |
|---|---|
| 事件身份 | `event_id`、名称、类型、状态、发生时间或窗口 |
| 事前快照 | 事前判断、路径、证据引用、冻结时间 |
| 实际事实 | 结果、来源、发布时间、修订状态 |
| 市场反应 | 对象、窗口、方向/幅度或缺失原因 |
| 判断复盘 | 命中状态、路径状态、关键偏差 |
| 可复用结论 | 下次观察点、风险提醒 |
| 输出 | 一页摘要、保存、重开、复制 |

### 5.5 事前快照原则

- 事件进入结果复盘后，不能用事后事实覆盖事前内容。
- 若历史记录从未保存过事前快照，必须显示：
  `NO_FROZEN_PRE_SNAPSHOT`
- 已知历史事件必须显示：
  `RETROSPECTIVE`
- 缺少事前快照不阻止产品复盘，但不得宣称预测命中。
- 事后修订应新增版本或修订记录，不静默改写原事实。

### 5.6 首批真实事件验收集

首批至少完成三条真实复盘，覆盖三种不同类型：

1. 一项大型机构财报；
2. 一项关税、制裁或政策事件；
3. 一项地缘冲突或突发事件节点。

可追加一项已公布宏观数据，但不等待 `nfp_2026_07`。

### 5.7 RESULT 完成标准

全部满足才可声明 `EVENT_RESEARCH_RESULT_V1_PASS`：

- 至少三条真实事件完成复盘；
- 事件来自现有日历、新闻/inbox 或 registry，不重新手造重复事件；
- 同一事件保存重开仍为同一 `event_id`；
- 事前快照与事后事实明确分离；
- 实际事实有来源和时间，或明确标记缺失；
- 三条记录均能保存、关闭、重开；
- 三条记录均能生成可复制摘要；
- 单条正常复盘目标用时不超过十分钟；
- 已知历史事件明确标记 `RETROSPECTIVE`；
- 未来事件和未到发布时间的事件继续被事后门禁阻止；
- Human 能回答：“这份复盘以后是否值得再打开？”

### 5.8 RESULT 明确不做

- 不做模型评分和预测准确率排行榜；
- 不用历史事件冒充 held-out；
- 不自动生成未经确认的事实；
- 不重写 Graph、ScenarioReasoner 或证据引擎；
- 不新建平行 registry；
- 不先做复杂模板、全量财报字段或 AI 长研报；
- 不建设跨事件统计仪表盘；
- 不为每个字段、按钮或测试单独开审核环。

## 6. V3.1：REGISTRY 事件研究台账 + BADGE 状态标识

### 6.1 一句话目标

> 用户打开一个台账，就能看到所有真实事件当前处于什么阶段、下一步做什么，并能快速找到已完成复盘。

### 6.2 验收名

`EVENT_RESEARCH_REGISTRY_V1_PASS`

BADGE 不另设 PASS；它包含在本验收内。

### 6.3 台账必须回答的问题

每条记录必须让用户快速知道：

1. 这是什么事件？
2. 什么时候发生或预计发生？
3. 当前处于哪个生命周期？
4. 证据是否新鲜、是否缺失？
5. 下一步该做什么？
6. 是否已经形成结果与复盘？

### 6.4 台账视图

至少支持：

- 全部活跃事件；
- 即将发生；
- 持续跟踪；
- 已发生待复盘；
- 已完成复盘；
- 已归档。

最小筛选维度：

- 生命周期；
- 事件类型；
- 时间范围；
- 是否有事前快照；
- 是否待补结果；
- 证据状态。

不在 V3.1 建设复杂自定义查询器。

### 6.5 BADGE 状态语言

BADGE 是统一状态的可视表达，不是独立功能。

每条事件最多展示：

- 一个主生命周期标识；
- 最多两个辅助风险/行动标识。

主标识示例：

- 待纳入
- 事前跟踪
- 持续事件
- 待确认结果
- 已复盘
- 已归档

辅助标识示例：

- 缺事前快照
- 证据过期
- 时间待核验
- 已知历史复盘
- 结果有修订
- 来源不足

禁止：

- 同一状态在不同页面使用不同颜色或名称；
- 页面根据零散字段自行猜状态；
- 用“绿色”暗示研究结论或数据质量已经 PASS；
- 一条记录堆叠大量徽章。

### 6.6 REGISTRY 用户动作

台账中的下一步动作必须与生命周期一致：

| 生命周期 | 首要动作 |
|---|---|
| `CANDIDATE` | 纳入研究 |
| `TRACKING_PRE` | 补事前或刷新证据 |
| `OCCURRED_PENDING_RESULT` | 确认结果并复盘 |
| `ONGOING` | 记录新节点 |
| `REVIEWED` | 打开复盘或复制摘要 |
| `ARCHIVED` | 查看或恢复 |

不得从台账绕过未来事件门禁。

### 6.7 REGISTRY 完成标准

全部满足才可声明 `EVENT_RESEARCH_REGISTRY_V1_PASS`：

- 现有 registry 仍为唯一真相源；
- 已有事件无需迁移到平行存储；
- 台账能够展示上述主要生命周期；
- 至少包含即将发生、持续、待复盘、已复盘四类真实记录；
- 筛选后能够稳定打开正确 `event_id`；
- 下一步动作与生命周期一致；
- RESULT 复盘可从台账重开；
- BADGE 在日历、待办、台账使用同一状态语义；
- 错误、缺失、过期和未知状态可见；
- Human 能在一分钟内找到“现在最该处理的事件”。

### 6.8 REGISTRY 明确不做

- 不做多用户协作、权限和团队分配；
- 不做云同步和公开发布；
- 不做复杂标签体系或无限自定义字段；
- 不做全量投资组合分析；
- 不把 BADGE 单独开成第三个研发环；
- 不为视觉微调重复开启 R1。

## 7. V3 整体产品验收

### 7.1 验收名

`EVENT_RESEARCH_PRODUCT_V3_PASS`

### 7.2 整体人话验收

> 我能把真实事件纳入跟踪；事件发生后完成一页复盘；以后从台账找到它、看懂当前状态，并知道下一步做什么。整个过程不需要重复造事件，也不会把历史复盘冒充前瞻研究。

### 7.3 整体完成条件

V3.0 与 V3.1 均 PASS，并由 Human 完成一次产品路径验收：

1. 从日历或事件源打开一条已发生事件；
2. 进入同一研究记录；
3. 查看事前快照；
4. 确认实际事实和来源；
5. 完成判断与路径复盘；
6. 保存并复制摘要；
7. 返回台账；
8. 通过状态或筛选重新找到该事件；
9. 重开后内容一致；
10. Human 确认该流程具有重复使用价值。

### 7.4 V3 不受未来日期阻塞

- V3.0 使用已发生事件完成 RESULT 验收。
- 尚未发生事件只验收事前跟踪与门禁，不等待其自然发生。
- `nfp_2026_07` 可继续保留为将来的真实 forward 证据，但不是 V3 放行条件。
- live-forward、held-out 和 `RESEARCH_PASS` 继续属于 RES 轨道。

## 8. 真实事件选择原则

### 8.1 选择顺序

优先选择：

1. 已有 `event_id` 和来源；
2. 已存在事前记录或路径；
3. 结果已经公开；
4. 能观察到至少一个市场或传播结果；
5. 类型差异明显。

### 8.2 来源原则

- 官方公告、监管披露、公司财报、政府或国际机构信息优先；
- 新闻报道可作为辅助来源；
- 无法核实的社交媒体内容不得作为唯一实际事实；
- 来源过期、缺失、冲突必须显式显示；
- 不在仓库保存受限原文，只保留安全引用、摘要和时间。

### 8.3 历史复盘边界

历史事件的价值是：

- 验证产品流程；
- 整理事实和传播机制；
- 积累可复用观察点。

历史事件不能单独证明：

- 模型预测有效；
- 系统达到研究门槛；
- forward 表现通过；
- 可用于对外宣传的准确率。

## 9. 产品指标

V3 先衡量使用价值，不用测试数量代替产品成效。

### 9.1 核心指标

| 指标 | 目标 |
|---|---|
| 真实事件复盘完成数 | V3.0 首批至少 3 条 |
| 单条复盘时间 | 正常目标不超过 10 分钟 |
| 重复造事件 | 0 |
| 保存重开一致 | 100% |
| 实际事实来源可见 | 100%，或明确缺失 |
| 历史复盘标识 | 100% |
| 台账找出首要待办 | Human 目标 1 分钟内完成 |
| 可复制结果摘要 | 每条 REVIEWED 记录均具备 |

### 9.2 反指标

出现以下情况说明 V3 偏离产品目标：

- 新增大量字段但真实事件仍无法完成复盘；
- 测试数量增加，但用户仍不知道下一步；
- 页面变复杂，单条复盘时间反而上升；
- 新建第二套事件或结果存储；
- 事后事实覆盖事前判断；
- 为等待未来事件而停止产品验收；
- BADGE 数量多于有效行动信息；
- 以历史复盘结果升级 `RESEARCH_PASS`。

## 11. 风险与控制

| 风险 | 影响 | 控制 |
|---|---|---|
| 事后信息污染事前记录 | 无法诚实复盘 | 冻结事前快照；缺失则显式标记 |
| 历史复盘冒充前瞻证据 | 错误研究结论 | 强制 `RETROSPECTIVE`，与 RES 轨道隔离 |
| 实际事实来源不可靠 | 复盘失真 | 来源和时间必填或显式缺失 |
| 突发事件无明确终点 | 无法进入结果状态 | 支持 `ONGOING` 与阶段性复盘 |
| 状态体系膨胀 | 用户看不懂 | 单一生命周期；一个主标识、最多两个辅助标识 |
| REGISTRY 变成新系统 | 重复存储与维护 | 复用现有 registry，不另造真相源 |
| 为技术完整性拖延产品 | 再次失去产品成效 | 只修产品阻断与事实错误；其他登记技术债 |
| 等待未来日期 | 主线停滞 | 用已发生真实事件完成 V3.0 |

## 12. 回滚与保留

### 12.1 回滚原则

- RESULT 新字段或页面必须保持既有 V2 记录可打开。
- 新状态无法解析时降级为“状态未知”，不得损坏记录。
- 关闭 RESULT 入口后，V2 日历、待办和就地执行仍可使用。
- REGISTRY 新筛选和 BADGE 可整体关闭，不影响底层 registry。

### 12.2 必须保留

- 既有 `event_id`；
- 服务端 registry 单一真相源；
- 事后生成门禁；
- refs 与证据新鲜度；
- V2.2–V2.7 已完成能力；
- AI refs disarmed、研究结论隔离等现有硬边界。
